## 2. 通用施工纪律

1. 每阶段先检查当前实现和契约，再写代码。
2. 每个 bug 先增加可复现测试。
3. 每个子任务尽量修改 1-3 个文件；超过 3 个文件时继续拆分。
4. 新依赖先写出用途、替代方案和取舍，只采用本文批准的依赖。
5. 关键业务路径有明确异常和上下文日志。
6. 格式问题交给 Ruff，类型问题交给 Pyright。
7. 本地测试、formatter、linter、类型检查均通过后提交。
8. 模块间通过 JSON 契约和 CLI 连接，避免跨包导入私有实现。
9. 不提交 `.env`、runtime 运行数据、API Key、Workspace ID 和用户绝对路径。
10. 每个阶段结束输出：变更文件、执行命令、测试结果、边缘情况、剩余风险和下一阶段入口。

### 2.1 提交粒度

建议提交前缀：

```text
harness: ...
skills: ...
evaluation: ...
web: ...
ci: ...
docs: ...
```

每个提交围绕一个可独立审查的目标。单个 PR 建议控制在 200-400 行改动；实现量较大时使用阶段分支或堆叠 PR。格式类改动与逻辑类改动分开。

## 12. 边缘情况与测试用例

### 12.1 配置

- `.env` 缺失
- API Key 为空
- Base URL 含占位符
- Base URL 与 Key 地域不一致导致 401
- reasoning effort 非法
- max iterations 为 0 或过大

### 12.2 来源

- PDF 无文本
- DOI 与标题冲突
- PubMed 无结果
- Crossref 限流
- URL 重定向到非允许域名
- 同一论文多来源重复
- 来源摘要为空

### 12.3 模型

- 超时
- 429
- 5xx
- 结构化输出缺字段
- 引用未知 source ID
- 假设数量少于 3
- 模型产生越权操作

### 12.4 路线

- 路线目录少于 90
- 模式分布错误
- GeoJSON 缺路线
- selected route ID 不存在
- 无符合距离门禁路线
- 接驳距离缺失

### 12.5 环境

- dashboard 缺失
- 路线环境少于 90
- 数据过期
- 未来时段缺 PM2.5
- 花粉 no_data

## 14. 交给 Codex 的后续审查重点

Qoder 完成后，Codex 按阶段审查：

1. 状态机与恢复是否存在隐性状态。
2. Adapter 是否允许命令注入或路径越界。
3. 引用门禁是否覆盖模型输出全部引用字段。
4. 实验是否存在用同一综合分自证的循环。
5. 结果状态与预注册阈值是否一致。
6. 评价模块窄接口是否复用原有评分。
7. 网页 payload 是否脱敏。
8. 测试是否覆盖失败路径。
9. 新依赖是否全部有用途。
10. CI 是否在无网络、无 Secret 环境稳定运行。
