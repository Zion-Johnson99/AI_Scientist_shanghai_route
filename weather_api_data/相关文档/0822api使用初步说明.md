## 2. 当前可用数据

| 数据 | 当前权限 | 时间性质 | 适合用途 |
|---|---|---|---|
| 温度、相对湿度、体感温度、风、气压、能见度、UV、降水 | 标准实况 | 当前观测快照 | 路线卡片当前状态、热风险判断 |
| 温度、相对湿度、风、降水概率等 | 标准逐小时 | 未来1/12/24/72小时 | 选择今天哪个时段运动；`details=true` 才有完整字段 |
| AQI、PM2.5、PM10、O₃、NO₂、SO₂、CO | 标准空气质量 | 当前观测快照 | 当前空气健康风险 |
| PM2.5 等逐小时空气质量 | 进阶、未开通 | 未来24小时 | 按出发时间预测暴露 |
| 历史温湿度实况 | 进阶、未开通 | 过去6/24小时 | 当日回顾曲线 |
| 运动、晨练、路况、空气扩散、过敏等指数 | 标准1日指数 | 每日 | 辅助解释与全局运动门控 |
| 分钟降水 | 标准、中国区域 | 未来约2小时 | 用户准备出发时按需查询 |
| 噪声 | 无相关接口 | — | 需外部来源 |
| 直接花粉浓度 | 无明确标准接口 | — | 目前只有过敏风险等间接指标 |

[实况天气文档](https://platform.weathercn.com/doc/api/current-weather.html)明确包含相对湿度等字段；[逐小时完整字段表](https://platform.weathercn.com/apidoc/api-hourly-forecast.html)还列出了未来逐小时相对湿度、湿球温度、露点、风速和太阳辐照度。[空气质量接口](https://platform.weathercn.com/doc/api/air-quality.html)提供当前 PM2.5 等六项污染物。

最关键的时间边界是：

- “未来一天温湿度”现在就能取，一次 `24hour` 请求返回24条逐小时预报。
- “未来一天 PM2.5”依赖进阶空气质量预报。
- “过去一天温湿度”依赖进阶历史实况。
- “过去一天 PM2.5”在当前权限列表里没有历史端点。

自己连续轮询并长期保存 PM2.5，可能接近平台收费历史产品的能力范围。建议先向 `support@weathercn.com` 书面确认滚动24小时留存和二次评分用途；[服务协议](https://platform.weathercn.com/doc/terms.html)还要求在已登记的应用载体内使用、标注华风爱科来源，并限制二次发布和数据调整。

## 3. 每日500次的接入方式

推荐“四个气象采样区上限”，初步覆盖：

1. 徐汇滨江—龙华
2. 上海植物园—华泾
3. 康健—漕河泾
4. 徐家汇—衡复风貌区

每小时每区执行一次定位、实况天气、当前空气质量，共 4 × 3 × 24 = 288 次；24小时天气预报每天刷新4轮，增加16次；生活指数每天增加4次；上海预警每小时增加24次；分钟降水按需预留40次。计划用量约372次，450次设置为程序硬上限，最后50次留给异常和人工检查。

官方[开发标准](https://platform.weathercn.com/doc/dev-standard.html)带来几项实现约束：

- 定位结果禁止持久化，经纬度四舍五入到3位小数。
- 根据响应 `Expires` 控制刷新时间，数据仍有效时跳过新请求。
- 启用 GZIP，调用错峰，实际节流控制在4 QPS以内。
- 分钟降水返回 HTTP 400 时记录为“当前区域无数据”，避免反复重试。

宣传页提到5公里网格预报，但你的标准端点仍通过 Location Key 获取数据，空气质量还来自观测站/发布机构。因此四个坐标可能返回相同或相近的 Location Key。若实测结果高度重复，收缩为一个徐汇位置更合理；温湿度和 PM2.5 此时主要影响运动时段，难以拉开徐汇内部90条路线的排名差距。[产品说明](https://platform.weathercn.com/products/)

## 4. 噪声与花粉

WeatherCN 当前没有噪声字段。上海官方可提供两层基础资料：

- [2025年声环境功能区划](https://sthj.sh.gov.cn/cmsres/e7/e7ec8231f0a1432c92c20c9aef5f8e4e/0ef738f3511175acce601d3bed3786c3.pdf)可划分2类、3类和交通干线4a类区域，适合形成静态噪声风险底图。
- [城市功能区声环境月报](https://sthj.sh.gov.cn/hbzhywpt1143/zshjzlyb/index.html)只有分类达标率，缺少街道实时分贝。

可补充 [NoiseCapture 开放数据](https://noise-planet.org/noisecapture_exploit_data.html)：其 WFS 提供约15米六边形的 LAeq、LA50、测量次数和时间。我的徐汇范围只读查询得到90个六边形、7579秒测量，其中68个单元最后测量年份为2026，最新记录为2026-08-16；覆盖仍呈零散轨迹，手机校准和采样时段差异较大，适合校准“估算噪声风险”，暂不适合作为全区实时分贝。

花粉方面：

- WeatherCN 的[指数列表](https://platform.weathercn.com/doc/resources/indices.html)包含 ID 127“过敏指数”，标准1日[生活指数接口](https://platform.weathercn.com/doc/api/life-index.html)理论上可返回。它属于每日风险等级，缺少花粉浓度、植物种类和街道差异，需要后续用一次真实请求确认上海返回内容。
- 上海官方规划提出建设花粉监测站和花粉服务产品，但截至本轮查询，市气象局和公共数据平台公开入口尚未发现机器可读的街道级 API。[上海气象服务规划](https://www.shanghai.gov.cn/202119bgtwj/20211008/9326d090c3374044bbd17e8aa620942c.html)
- Google Pollen API 提供最高1公里、未来5天数据，但中国目前只覆盖草类花粉；月度免费额度5000次，之后首档价表为每1000次10美元。其缓存、署名和地图展示条款与当前高德地图界面存在明显冲突，暂不推荐进入主线。[覆盖范围](https://developers.google.com/maps/documentation/pollen/coverage?hl=zh-CN)、[价格](https://developers.google.com/maps/billing-and-pricing/pricing)、[使用政策](https://developers.google.com/maps/documentation/pollen/policies)

更稳妥的街段级花粉方案是：WeatherCN 每日过敏指数作为全区时间系数，再结合公园/绿地覆盖、植被季节、降雨、风和道路两侧绿化生成“花粉风险估算”，界面明确标注模型值与置信度。

### 这把 Key 能获取什么

| 权限 | 可用数据 | 时间性质 |
|---|---|---|
| `airQuality` | AQI、PM2.5、PM10、O3、CO、NO2、SO2 | 当前实况 |
| `airQualityPremium` | AQI、PM2.5、PM10 等 | 未来24小时逐小时预报 |
| `currentconditions` | 温度、相对湿度、体感温度、风、气压、能见度、降水 | 当前及过去6/24小时实况 |
| `forecasts24hour` | 温度、湿度、降水、风等 | 未来24小时逐小时预报 |
| `forecasts10day` | 最高/最低温、天气、降水等 | 未来10天逐日预报 |
| `alerts` | 气象灾害预警 | 实时更新 |
| `indices`、`indices5day` | 运动、过敏、道路等生活指数 | 当日及未来5天 |
| `locations` | 经纬度转 LocationKey | 调用其他接口前使用 |

关键区别：

- “过去24小时温湿度”是滚动24小时实况，使用 `currentconditions/.../historical/24?details=true`，通常返回逐小时记录及 `Temperature`、`RelativeHumidity`。[实况接口指南](https://apidoc.weathercn.com/developers/currentConditionsAPIGuide.html)
- “逐小时PM2.5”是未来24小时预测，使用 `airqualityforecast/v1/hourly/24hour/{LocationKey}`；当前PM2.5另走 `airquality/.../observations`。[空气质量接口指南](https://apidoc.weathercn.com/developers/airQualityAPIGuide.html)
- 当前权限中没有历史逐小时PM2.5接口，所以无法直接回取昨天每小时PM2.5；后续可定时采集当前值，形成项目自己的时间序列，但长期保存范围需向服务方确认授权条款。
- `indices` 可能提供过敏风险指数，仍然没有花粉浓度或花粉种类；噪声数据也不在这组权限内。

### 进阶 Key 的用法

调用链为：

`经纬度 → LocationKey → 生成认证参数 → 请求气象/空气质量 → 标准化输出`

认证方式与此前标准 Key 不同：

1. UTC 时间生成11位 `requestDate`。
2. 拼接 `API Key + 换行 + 接口类型 + 换行 + requestDate`。
3. 使用 Secret 做 HMAC-MD5，结果经 Base64 和 URL 编码得到 `accessKey`。
4. 请求参数包含 `apikey`、`requestDate`、`accessKey`；Secret只留在服务端。

附件中的 Java 示例仅适合作为签名算法参考，代码片段不完整，并且使用了较旧的 HTTP 客户端。实际接入适合用现有 Python `requests`，无需新增依赖。[基本示例](https://apidoc.weathercn.com/developers/samples.html)

开发时还要落实：

- 经纬度保留3位小数，定位结果不落盘缓存。
- 请求头带 `Accept-Encoding: gzip,deflate`。
- 根据响应 `Expires` 控制刷新时间，并加入随机抖动。
- 中国地区优先读取 `LocalSource.Id = 7`。
- 日志隐藏完整请求 URL、API Key、Secret 和 `accessKey`。[开发规范](https://apidoc.weathercn.com/developers/best-practices.html)
