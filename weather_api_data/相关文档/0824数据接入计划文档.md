# 0824数据接入计划文档

## 1 目标和边界

第一阶段在 weather_api_data 内建立独立的华风爱科数据接入模块，暂时保持 xuhui_route_builder 零改动。

当前以进阶 Key 为数据源，负责签名、请求、解析、空间来源发现、去重、刷新控制和 JSON 导出。标准 Key 进入安全配置并保持关闭，只保留一次性定位探针作为人工确认入口。

空间数据直接采用接口返回的 LocationKey、空气质量来源和覆盖关系。系统保留真实差异，不进行 1 千米估计、空间插值或道路级 PM2.5 建模，也不把相同来源拆成多个片区。

首版接入以下数据：

1. 当前 PM2.5、AQI 和主要污染物。
2. 当前温度、湿度、天气和风。
3. 过去 24 小时天气实况。
4. 未来 24 小时逐小时天气和空气质量。
5. 当天生活指数，包括晨练、空气污染扩散、运动、过敏、交通和路况。
6. 当前有效气象预警。

生活指数按日发布。交通和路况指数描述天气影响，不代表实时拥堵或逐条道路通行状态。当前权限未提供历史逐小时 PM2.5 端点，首版不展示过去 24 小时 PM2.5。

在服务方书面确认长期保存和项目内计算权限后，模块同时建立本地历史库。历史回填最多覆盖一个自然年，优先选择 2025 年 1 月 1 日至 12 月 31 日；日常采集数据从正式运行日开始滚动保留 365 天。定位接口响应、认证参数和完整请求 URL 不进入历史归档。

## 2 接入方式

### 2.1 进阶 Key

1. 测试域名使用 apidev.weathercn.com。
2. 正式域名使用 api.weathercn.com，启用前核实账号授权。
3. 认证参数包含 API Key、Secret、UTC 时间片和 HMAC-MD5 签名生成的 accessKey。
4. 当前主线使用进阶 Key 请求真实数据。

已知权限包括 locations、currentconditions、forecasts24hour、forecasts10day、airQuality、airQualityPremium、indices、indices5day 和 alerts。首版只实现本计划列出的必要接口，10 日天气预报留到后续需求。

### 2.2 标准 Key

1. 域名使用 openapi.weathercn.com。
2. 认证使用 `apikey` 查询参数。
3. WEATHERCN_STANDARD_ENABLED 默认设置为 false。
4. 标准客户端只开放一次定位探针，首次尝试后关闭当前客户端实例的探针入口。
5. 测试确认关闭状态下没有网络请求入口。

### 2.3 地理标识

LocationKey 是服务地理标识，空气质量响应中的来源字段用于记录观测或发布来源。系统分别保存两类信息，避免把 LocationKey 写成监测站编号。

徐汇区公开国控点包含徐汇上师大，其他市控点和小微站是否出现在结果中取决于华风接口。系统只记录候选坐标实际返回的来源。

## 5 进阶签名和请求规则

### 5.1 签名流程

1. 使用 UTC 当前时间生成 yyyyMMddHHmm。
2. 删除最后一位分钟数字，得到 11 位 requestDate。
3. 使用 API Key、换行符、全小写 apiContentType、换行符和 requestDate 组成待签名文本。
4. 使用 Secret 执行 HMAC-MD5。
5. 对结果执行 Base64 编码和 URL 编码，得到 accessKey。
6. 请求参数携带 apikey、requestDate 和 accessKey。

签名测试使用固定 UTC 时间和假凭据，覆盖换行格式、HMAC-MD5、Base64 和 URL 编码。

### 5.2 通用请求规则

1. 定位坐标保留 3 位小数。
2. 请求头加入 Accept-Encoding: gzip,deflate。
3. 使用 HTTPS、明确超时和单线程保守限速。
4. 中国地区优先选择 LocalSource.Id 等于 7 的数据。
5. 同一 LocationKey 的同一接口在一轮运行中只调用一次。
6. 定位结果只在当前运行复用，不跨运行持久缓存。
7. 根据 Expires 和 valid_until 判断刷新与过期状态。

## 6 接口范围

### 6.1 定位

接口路径为 locations/v1/cities/geoposition/search。输入为经纬度，进阶接口返回单个定位对象；输出保存 LocationKey、行政区、坐标、时区和本地数据源。

### 6.2 当前和历史天气

1. currentconditions/v1/{LocationKey} 获取当前天气。
2. currentconditions/v1/{LocationKey}/historical/24 获取过去 24 小时天气实况。
3. 保存温度、湿度、体感温度、天气文字、天气图标、风向、风速、阵风、气压、能见度、紫外线和降水。

### 6.3 未来天气

1. forecasts/v1/hourly/24hour/{LocationKey} 获取未来 24 小时逐小时天气。
2. 请求启用 details 和 metric。
3. 温度读取 `Temperature.Value`，风速读取 `Wind.Speed.Value`，阵风读取 `WindGust.Speed.Value`。
4. 保存预报时间、温度、湿度、天气、降水概率、降水量、风向和风速。
5. 当前进阶响应未提供 `Pressure`，逐小时气压按可选字段处理并保留为空。

### 6.4 当前空气质量

1. airquality/v1/observations/{LocationKey} 获取当前数据。
2. 保存 AQI、PM2.5、PM10、O3、NO2、SO2、CO、主要污染物、观测时间和来源。
3. 同一来源和观测时间的重复记录执行去重，不同来源分别保留。

### 6.5 未来空气质量

1. airqualityforecast/v1/hourly/24hour/{LocationKey} 获取未来 24 小时逐小时数据。
2. 保存预报时间、AQI、PM2.5、PM10、O3、NO2、SO2、CO 和等级描述。

### 6.6 生活指数

1. indices/v1/daily/1day/{LocationKey}/groups/100 获取当天指数。
2. indices/v1/daily/5day/{LocationKey}/groups/100 获取未来 5 天指数。
3. 提取晨练、空气污染扩散、交通、路况、运动和过敏指数。
4. 保存指数编号、名称、等级、说明、建议和日期。

### 6.7 气象预警

alerts/v1/{LocationKey} 获取有效预警，保存标题、类型、等级、生效时间、失效时间、发布机构和正文摘要。

## 7 徐汇区空间来源发现

### 7.1 发现流程

1. 候选点覆盖徐汇区各街镇和主要运动区域。
2. 首轮只调用 locations，统计唯一 LocationKey。
3. 再对每个唯一 LocationKey 调用当前空气质量，统计来源编号和名称。
4. 同一 LocationKey 对应的采样点共享天气请求。
5. 不同空气质量来源全部保留。
6. 响应缺少来源编号时记录 source_status=unknown，不根据距离推断站点。

候选点只用于发现接口提供的空间来源，不代表人为划定的气象片区。华风未开放的监测站不会进入结果。

### 7.2 去重和展示

1. 天气按 LocationKey 去重。
2. 空气质量按来源编号、来源名称和观测时间去重。
3. 生活指数按 LocationKey、指数编号和日期去重。
4. 预警按预警编号和发布时间去重。
5. 采样点与 LocationKey 的覆盖关系单独保存。

网页只展示接口真实返回的来源差异。多个坐标返回同一 LocationKey 或同一空气质量来源时，显示为同一数据区。天气和空气质量的来源数量允许不同。

每组数据保存 spatial_basis，取值为 location_key、observation_source 或 forecast_source。名称中避免使用 1 千米、道路级和站点实测等缺少响应证据的描述。

## 8 数据结构和输出

### 8.1 公共字段

1. schema_version。
2. provider，固定为 weathercn_advanced。
3. environment，取值为 test 或 production。
4. generated_at。
5. status，取值为 ok、partial、stale、no_data 或 error。
6. request_summary，记录计划调用数、成功数、失败数、跳过数和唯一 LocationKey 数量。

### 8.2 来源和质量字段

1. location_key 和 location_name。
2. probe_point_ids。
3. representative_longitude 和 representative_latitude。
4. local_source_id。
5. air_quality_source_id 和 air_quality_source_name。
6. spatial_basis 和 source_status。
7. observed_at、forecast_at、valid_until 和 fetched_at。
8. is_stale、completeness 和 missing_fields。
9. error_code 和 error_message。

### 8.3 单位

1. 温度使用摄氏度。
2. 相对湿度使用百分比。
3. 风速使用千米每小时，同时记录原始单位。
4. PM2.5 和颗粒物使用微克每立方米。
5. CO 保留接口单位并记录 unit。
6. AQI 保留接口标准和等级文字。

### 8.4 输出文件

1. environment_regions.json

保存 LocationKey、空气质量来源、采样点映射和来源数量。

2. environment_latest.json

保存当前天气、当前空气质量、当天生活指数和有效预警。

3. environment_hourly.json

保存过去 24 小时天气、未来 24 小时天气和未来 24 小时空气质量。

4. run_report.json

保存运行时间、调用统计、错误分类、数据完整度和输出校验结果。

5. route_environment.json

第一阶段只定义契约，暂不生成正式路线结果。后续记录 route_id、segment_id、location_key、air_quality_source_id、时间范围和环境数据引用。

所有 JSON 使用原子写入，避免网页读取未完成的文件。

### 8.5 历史存储格式

历史数据统一放在 D:\SJTU\交大\揭榜挂帅\AI_Scientist_develop\weather_api_data\runtime\history。标准化数据写入 weathercn_history.sqlite3。SQLite 适合当前数据规模，支持事务、唯一约束和时间范围查询，Python 标准库可以直接读写。

数据库按职责保存以下数据：

1. runs 保存每次运行的时间、环境、调用统计和状态。
2. weather_observations 保存天气实况和过去 24 小时实况。
3. weather_forecasts 保存逐小时天气预报，并区分 issued_at 和 forecast_at。
4. air_quality_observations 保存 AQI、PM2.5 和其他污染物实况。
5. air_quality_forecasts 保存逐小时空气质量预报，并区分 issued_at 和 forecast_at。
6. life_indices 保存生活指数日期、等级和建议。
7. alerts 保存预警内容和有效时间。
8. data_sources 保存采样点、接口来源、空间依据和单位说明。

每类数据尽量保留接口返回的完整业务字段，同时保存 dataset_role、fetched_at、observed_at、forecast_at、valid_until、source、unit、completeness 和 missing_fields。dataset_role 区分 backfill_2025 和 operational。观测值和预报值分开存放，避免后续训练时把预报误作实测标签。

脱敏原始响应使用 JSON GZIP，路径为 runtime/history/raw/YYYY/MM/DD/{run_id}。归档保留响应正文、接口类别、请求时间、HTTP 状态和响应头中的数据有效期，删除 API Key、Secret、accessKey、认证 URL 和定位接口响应。

### 8.6 保存范围和保留周期

1. 历史回填最多覆盖一个自然年，首个目标区间为 2025 年 1 月 1 日至 12 月 31 日。
2. 日常 operational 数据按记录对应的业务时间滚动保留 365 天。
3. 原始 JSON GZIP 按 fetched_at 滚动保留 365 天。
4. 清理任务先执行 dry_run，只删除 weathercn_history.sqlite3 中超过期限的 operational 记录和 runtime/history/raw 下经过绝对路径校验的过期文件。backfill_2025 由独立开关管理，不参与日常滚动清理。
5. 若权限只提供过去 24 小时天气和未来预报，程序跳过 backfill_2025，从正式运行日开始逐日积累，不补造缺失历史。
6. 当前已知权限没有历史逐小时 PM2.5，2025 年 PM2.5 回填只有在服务方开放对应数据后执行。
7. 长期归档、项目内二次计算和模型训练在服务方书面授权后启用，授权状态记录在运行配置和 run_report.json 中。

一年数据量预计处于数百 MB 量级；保留每轮完整压缩响应时可能达到数 GB，仍适合本地保存。程序在 dry_run 和 run_report.json 中统计数据库、原始归档和剩余磁盘空间。

## 9 配额、错误和日志

### 9.1 配额控制

1. 进阶 Key 的 QPS、每日配额和有效期以服务方确认为准，不沿用标准 Key 的 5 QPS 和每日 500 次配置。
2. 配额确认前只开放手动运行，使用单线程和保守限速。
3. 每次运行先执行 dry_run，显示预计调用次数和接口类别。
4. 配置单次调用硬上限，达到上限后停止新增请求并输出 partial。
5. HTTP 429 记录 Retry-After，并停止本轮非核心请求。
6. 正式调度在配额确认和最小验证通过后启用，任务加入随机延迟。

### 9.2 错误处理

1. HTTP 401 和 403 归类为认证或授权错误，停止本轮请求。
2. HTTP 400 按响应区分参数错误和当地无数据。
3. HTTP 500 至 599 和临时网络错误最多重试 2 次，使用递增等待和随机延迟。
4. JSON 解析失败时记录接口类别、LocationKey、状态和脱敏摘要。
5. 非核心接口失败时保留成功数据，总体状态设置为 partial。
6. 数据超过 valid_until 后设置 is_stale=true。

### 9.3 日志

日志使用 DEBUG、INFO、WARN 和 ERROR。上下文包含 run_id、接口类别、LocationKey、尝试次数和耗时，不记录认证参数和完整请求 URL。
